# ADR 0002: Versioned Ren'Py SDK adapter and verified installation

**Status:** Accepted<br>
**Date:** 2026-09-10

## Context

Ren'Py's command-line interface is not a stable API, its commands load project code,
and an SDK is a large executable dependency obtained as an archive. The editor needs
repeatable version behavior without treating untrusted projects or archives as data
only. Linux evidence for 8.5.3 is recorded in the
[SDK spike results](../research/RENPY_SDK_SPIKE_RESULTS.md).

## Decision

Use an adapter keyed to an exact supported Ren'Py release. The first adapter supports
8.5.3 and must reject an incompatible reported version before project operations.
Commands are a closed enum rendered as direct argument arrays; arbitrary executable
names, shell strings, and implicit CLI fallbacks are not allowed.

Compile, lint, test, run, warp, and distribution all load project code and therefore
require an explicit project-trust decision. Output is bounded, execution is timed,
the entire process group is cancellable, and structured diagnostics retain bounded raw
output for review. Warp is development-only.

SDK installation resolves an exact official release artifact, checks a repository-
reviewed SHA-256 before extraction, validates every archive member and link, extracts
to a private sibling stage, refuses an existing destination, and atomically promotes
only a complete install. SDKs, archives, generated bytecode, and packages stay outside
Git. There is no implicit latest-version upgrade and no decision to redistribute the
SDK.

## Consequences

Each new Ren'Py version requires reviewed command descriptors, checksum provenance,
fixture compile/lint/test/run/warp/build evidence, and an adapter compatibility change.
A user can inspect and revoke project trust independently of opening source as text.
Failures are explicit rather than silently retried with different commands.

The accepted boundary is platform-neutral, but only Linux has integration evidence.
Windows and macOS launcher, filesystem, cancellation, packaging, signing, quarantine,
and install/launch behavior remain Phase 0 gates before the adapter can be considered
cross-platform.

## Alternatives considered

- **Invoke arbitrary CLI strings:** rejected because it expands injection and
  compatibility risk.
- **Trust projects when opened:** rejected because parsing source does not require
  executing embedded Python.
- **Extract then verify:** rejected because untrusted archive content must not be
  written before integrity and containment checks.
- **Bundle or auto-update the SDK now:** deferred pending licence, size, update,
  platform, and supply-chain evidence.
